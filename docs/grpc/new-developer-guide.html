Nano RPC and the experimental nano.v1 gRPC interface

This guide explains how an application chooses between the established Nano RPC interface and RsNano’s experimental gRPC contract. Nano RPC is JSON-based but non-standard; it is not JSON-RPC. It remains the compatibility baseline. The nano.v1 contract currently covers a selected subset of node operations.

Choose an interface

Which interface should an application use?

Both interfaces observe one RsNano node. Choose Nano RPC for its established, broad surface. Choose gRPC when a typed contract and generated client bindings fit the application boundary. Do not treat the current gRPC contract as complete Nano RPC coverage.

01 · USE NANO RPC

Keep existing tools working

Use standard Nano RPC for scripts, direct JSON inspection, existing clients, or operations outside the current gRPC contract.

02 · USE gRPC

Define a typed service boundary

Use the add-on for backend services that benefit from generated models, gRPC status codes, and server-streaming methods.

03 · USE BOTH

Adopt and compare safely

Keep Nano RPC available during adoption. The conformance suite uses it as the semantic reference for the gRPC contract.

The boundary

How Nano RPC and gRPC reach RsNano

When the daemon enables the grpc feature, the gRPC server runs in the RsNano process. Nano RPC and gRPC handlers read the same node, ledger, network, and telemetry subsystems. They do not share a wire format or a complete method inventory.

Nano RPC

An HTTP request names an action and sends JSON fields. Its established surface includes ledger reads, node control, work, on-node custodial key-store operations, diagnostics, and other operations.

Intentional divergence

Where the gRPC interface differs

The add-on preserves relevant Nano semantics, then records its own type, validation, and transport rules. Treat the Protocol Buffer files as the authority for gRPC fields and status behavior.

Types replace response-shape conventions

Enums represent epochs, block subtypes, local states, and process results. oneof distinguishes state and legacy block forms.

Versioning starts in the package name

The schema lives under nano.v1. The versioned package leaves room for compatible schema evolution without changing the package name.

Errors use gRPC status codes

Malformed input maps to INVALID_ARGUMENT. Missing records and ledger prerequisites use NOT_FOUND or FAILED_PRECONDITION.

Portable encodings stay explicit

Raw amounts use decimal strings because many target languages lack unsigned 128-bit integers. Hashes use canonical uppercase hexadecimal strings.

nano.v1 is not a wallet-developer protocol

PublishStateBlock accepts an already signed state block with work. The current contract does not expose an on-node key store, seed phrases, private keys, signing, custodial-wallet lifecycle, or work generation. Any future node-hosted key-store protocol belongs under nano.custodial_wallet.v1, not nano.v1.

The contract is intentionally narrow

The roadmap targets included public, non-custodial Nano RPC operations. The current contract has 18 methods and does not represent the full Nano RPC inventory.

Intended advantages

Why use a Protocol Buffer contract?

The gRPC design gives application developers an inspectable schema, generated bindings, and explicit stream controls. These are design properties, not throughput or reliability benchmark claims.

One reviewed schemaservices.proto and types.proto define the boundary.
→
Generated bindingsLanguage tooling creates client models and method stubs.
→
Earlier mismatch detectionMany field and method mismatches can become build-time integration errors.

No JSON translation hop

The in-process server reads RsNano subsystems directly. It does not call Nano RPC as an intermediary.

Runtime discovery

When reflection is enabled, tools such as grpcurl can inspect the live contract.

Transport-level flow control

HTTP/2, deadlines, cancellation, and per-subscriber queues give backend clients explicit streaming controls.

Representation choices are reviewable

The schema records decisions such as decimal raw amounts, typed block variants, and local-state enums in one artifact.

Events

Event streams and ledger reconciliation

The contract provides independent streams for confirmations, block processing, elections, votes, and telemetry. A stream gives a local observation; the ledger establishes the state your application records.

1. ConnectSubscribe to the smallest event family and filter that supports the use case.
→
2. ObserveTreat each event as a live, at-least-once node observation.
→
3. ReconcileQuery the ledger after connection, reconnection, and each relevant event.
Do not use a stream as a durable event log.

Streams have no replay cursor or global ordering. Deduplicate events and reconcile after reconnecting. If a subscriber cannot keep up, its stream closes with RESOURCE_EXHAUSTED; the server does not silently discard events for that subscriber.

Start contributing

How to contribute to the gRPC interface

Read the contract first. Then trace one implementation and compare its stable behavior with Nano RPC on the deterministic development-network ledger.

Read the service and type definitions.

Read grpc_proto/proto/nano/v1/services.proto. Then inspect each referenced type in types.proto.

Trace one service method.

Match the generated trait to a handler under grpc_server/src/services/ and its RsNano subsystem.

Compare stable semantics with Nano RPC.

Use the existing RsNano RPC handler as the oracle. Normalize only documented representation differences.

Make untested work visible.

Add the method to ALL_METHODS. Mark a method NOT TESTED until its scenario executes.

Run the required verification loop.

Format the workspace, run focused tests, check the feature-enabled daemon, then run ./grpc_conformance/run.sh.
